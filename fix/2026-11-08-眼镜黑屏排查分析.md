## 一、故障时间线与三层叠加问题

本次黑屏不是单一故障，而是**三层问题叠加**，逐层剥开后各击破：

| 层 | 症状 | 根因 | 修复 | 状态 |
|---|---|---|---|---|
| 1 | 点亮后眼镜收黑帧 | `light-on.sh` 重启 SurfaceFlinger 打废已运行 launcher 的 Unity SurfaceView 缓冲队列（每帧 `requestBuffer failed: BAD_VALUE`） | force-stop + 重启 launcherx 重建 surface | ✅ 已闭环（README 已记） |
| 2 | launcher 收"关机通知"停 VR 流程 | **我们 R1 补丁引入的回归**：monitor 跑起来后，电池通道 Broken pipe 恒读 0 → `battery is below 5` → `handleGlassShutdown` → 发 0x3ef(1007) 给客户端 → launcher 放弃 VR 准备 | processBattery 的 below-5/below-20 分支 no-op 化（smali 补丁） | ✅ 已验证生效 |
| 3 | launcher `dev_open` 失败 → Unity `OnApplicationQuit` 自杀 | **结论已修正（见第七章）**：守护把 `/dev/hwvr1` 指到 `hidraw0`（12d1:1092 CV10，report 1 只有 1 字节），而 `ioGetVendorInfo` 要发 `HIDIOCGFEATURE(4)`/report 1 → 必然失败；`vendorId=0` 是失败结果，不是原因。**不是 MCU 卡死** | 把 `/dev/hwvr1` 指向 `hidraw1`（12d1:107E input3，59B IMU / 127B feature）→ 实测 `ioGetVendorInfo` 失败 0 次、`dev_open` 成功、vendorId=4817 | ✅ 根因已定位，判据待固化 |

另有一条独立支线：vrhandle 的 `VrDeviceService` 崩溃循环（`ClassNotFoundException: BuildEx$VERSION`），已通过 hwframework.jar 类注入修复。

## 二、层 2：电池假 0 触发关机通知（R1 补丁回归）

### 2.1 取证链

1. 新 VRService 进程一启动即打印：
   `init battery → BATTERY value: 0 → battery is below 5, notify client and shutdown`
2. smali 追踪调用链：
   - `VRDeviceNodeMonitor.processBattery(0)` → 发消息 **0x12** 给 mHandler
   - VRService 收 0x12 → `handleGlassShutdown()`
   - `handleGlassShutdown` **不直接关眼镜**，而是发 **0x3ef(1007)** 给客户端（launcher）
   - launcher 收 1007 后放弃 VR 准备流程（VRPrepareActivity 空等 → 退出）
3. 电池恒 0 的原因：`IoGetBatteryStatus` 对本机走 **Broken pipe**（眼镜 MCU 电池查询通道不就绪），读数永远是垃圾 0。

### 2.2 关键认知

- **补丁前 monitor 根本不跑**（这是原来 R1 要修的问题），所以永远不会有这条关机通知——黑屏反而是"修好 monitor"带来的新暴露面。
- below-5（0x12 → 关机通知）和 below-20（0x11 → 低电量弹窗）两个分支都基于假 0 值，**全部封掉**是安全的：真实电量上报走 vcom BATTERY 帧，但本机 MCU 通道 Broken pipe，本来就没有真实电量可用。

### 2.3 修复方式

`VRDeviceNodeMonitor.processBattery` 中 below-5 / below-20 两分支的"发消息 + return"指令序列整体删除
（保留日志行，便于观察；`return-void` 保留，方法直接无操作返回）。

- 工具：`fix/patches/vrdesktop/fix_battery_noop.py`（对 smali 目录幂等注入）
- 已重打 `build/tmp/vrsvc/prox-signed.apk` 并装机验证：日志仍打印 `battery is below 5`（说明代码走到了），但**不再发 0x12 消息**，launcher 不再收到关机通知。
- 需要把该补丁并入 `apply_monitor_patch.sh` 一键流程并更新 `fix/apks/com.huawei.vrservice.apk`（见"待办"）。

## 三、vrhandle 崩溃循环：BuildEx$VERSION 类注入

### 3.1 崩溃取证

```
FATAL EXCEPTION: vrhandle
ClassNotFoundException: com.huawei.android.os.BuildEx$VERSION
  ← j0.j (ReporterFactory, 华为云上报组件) 静态初始化
```

- 触发点：vrhandle 的 VrDeviceService 启动 → 初始化华为云上报 → 引用华为 ROM 专有类 `BuildEx$VERSION` → 非华为 ROM 没有 → 崩。
- 崩溃循环期间 vrhandle 不持有 hidraw，launcher 能开设备；**修好 vrhandle 后它开始持有 `/dev/hidraw0`**，与 launcher 形成设备竞争（层 3 问题的一部分）。

### 3.2 类来源

用户提供的 ROM 树 `系统/tree/system/system/framework/hwframework.jar`（P30 鸿蒙固件解包）里确认含 `BuildEx` 类族：

- `com/huawei/android/os/BuildEx.smali`
- `com/huawei/android/os/BuildEx$VERSION.smali`
- `com/huawei/android/os/BuildEx$VERSION_CODES.smali`
- 依赖干净：仅需 `SystemProperties` + `@HwSystemApi` 注解（该注解不在 hwframework.jar 里，手写了空注解类 `com/huawei/annotation/HwSystemApi.smali`）

### 3.3 构建坑位记录

1. **新版 baksmali 输出带 hidden-api 标记**（`whitelist`/`blacklist`/`greylist` 前缀），老 smali 汇编器不认 → sed 清洗后重编。
2. **追加 classes2.dex 方案失败**：安装包里确实有 classes2.dex（unzip 验证过）、dex 内容完好（baksmali 回读验证过），但运行时仍 ClassNotFoundException —— 疑似 vdex/oat 缓存只覆盖 classes.dex。
3. **最终方案：把 BuildEx 类族直接合并进主 smali 树整体重编 classes.dex**（replace_dex.py 替换）→ 一次成功。

### 3.4 验证结果

合并版安装后观察 90 秒：**无新 FATAL**（crash buffer 里的 9 条全是 01:57 的旧记录），vrhandle 进程稳定存活并正常处理消息。

## 四、层 3：dev_open 失败（原判 MCU 卡死，已被第七章实测证伪）

> ⚠️ 本章 4.4「物理拔插 USB 让 MCU 复位」的结论**已作废**，不必再等用户操作。
> 真正根因是 `/dev/hwvr1` 选错接口（软件判据 bug），详见第七章。以下保留原始取证。

### 4.1 现象

launcher 的 WalleDev `dev_open` 失败：`ioGetVendorInfo failed, vendorId=0` → 判定眼镜不在位 → Unity `OnApplicationQuit()` 自杀（显示后约 5~7 秒退出）。

### 4.2 排除项（都验证过、都不是根因）

| 嫌疑 | 验证结果 |
|---|---|
| SELinux 拦截 | dmesg 有 `avc: denied ... hidraw0`，但 **permissive=1 只记录不拦截** |
| USB autosuspend | `runtime_status=active`, `control=on` |
| hidraw0 身份 | 确实是眼镜控制接口（CV10, 12d1:107E 系） |
| 守护/节点 | `/dev/hwvr1` 符号链接、hidraw 权限都正常 |
| vrservice monitor 独占 | 停掉 vrservice 后 dev_open 依旧失败 |

### 4.3 关键实验发现

1. **USB 重枚举**（`echo 1-1.1 > unbind; sleep 3; bind`）后：`ioGetVendorInfo` 成功读出 `vendorId=4817(0x12D1), productId=4222(0x107E)` —— 证明根因是 **眼镜 USB 接口/MCU 状态卡死**，重枚举可短暂救活。
2. **hwvr1 指向 hidraw1 时 vrhandle 短暂成功**（02:29:12），切回 hidraw0（CV10 控制接口）后又失败 —— 提示 0x107E（HID 数据接口）与 CV10（控制接口）的行为差异值得深挖。
3. 之后 vrhandle 进程也退出，dev_open 再次全面失败 —— 状态再次卡死。

### 4.4 待执行的决定性动作

**用户物理拔插眼镜 USB 线（等 5 秒再插回）** —— 让眼镜 MCU 完全断电复位。远程 unbind/bind 只复位了 USB 主机侧，MCU 侧状态未清。

拔插后验证命令：

```sh
adb shell logcat -c
adb shell am start -n com.huawei.vrlauncherx/.MainActivity
adb shell logcat -d | grep -E 'dev_open|ioGetVendorInfo|OnApplicationQuit'
```

期望：`vendorId=4817` 且无 `OnApplicationQuit`，前台保持 `com.huawei.vrlauncherx/.MainActivity`。

### 4.5 后续方向（若拔插后仍复发）

1. **vrhandle 与 launcher 的 hidraw 竞争**：vrhandle 修好后持 hidraw0，launcher 也要开 → 需要梳理两者对控制接口的共享/互斥策略（原厂上 vrhandle 可能靠华为框架内部协调）。
2. **hwvr1 符号链接指向策略**：守护目前把控制接口（描述符 `06 ff 00`）链到 hwvr1；实验提示 hidraw1（0x107E 数据接口）反而让 dev_open 成功 —— 值得做 A/B 对比。
3. **USB 重枚举自动化**：若 MCU 卡死复发，可在守护脚本里检测 `ioGetVendorInfo vendorId=0` 后自动 unbind/bind 重枚举（比断电轻量，但 MCU 侧不一定复位得动）。

## 七、实测复核：真机启动 VR 桌面，根因重新定位（2026-11-08 15:36–15:56）

> 触发：用户要求「无线 adb 连接 192.168.43.133，启动 vr 桌面，分析为什么无法启动」。
> 全程 `adb connect 192.168.43.133:5555` 在线，只读取证 + 可逆的运行时 A/B 实验，
> **未改设备文件、未刷机、未改开机逻辑**。日志落盘 `build/tmp/analysis-1108-*.log`。

### 7.1 连接与启动复现

```sh
adb connect 192.168.43.133:5555
adb -s 192.168.43.133:5555 logcat -c
adb -s 192.168.43.133:5555 shell am start -W -n com.huawei.vrlauncherx/.MainActivity
# Status: ok / LaunchState: WARM / TotalTime 4281ms —— 但 20 秒后栈顶仍是
# com.huawei.vrlauncherx/com.huawei.client.vrservice.activity.VRPrepareActivity
# （或退回 com.droidlogic.mboxlauncher/.Launcher），进程 pid 不断更换
```

### 7.2 直接失败链（第一轮，`start1.log`）

```
E DevHid: [WalleDev.cpp:ioGetVendorInfo](471): ioGetVendorInfo failed, ret(-1)
I DevHid: [WalleDev.cpp:openDev](118): openDevice success, fd=267, vendorId=0, productId=0
E DevHid: [WalleDev.cpp:dev_open](886): open device failed or get vendor data failed! return (-1)
E IMM_DM / DMManager: dev WalleDev open error
E IMM_IM : loadDevLibs WalleAlg error → createModule WalleAlg error
I Unity_HVRRenderMgrCore: HVRRenderMgrCore OnApplicationQuit()
```

**认知修正**：`vendorId=0` 与 `ioGetVendorInfo failed` 每次成对出现，它是**失败的结果**，
不是独立故障。文档第四章把 vendorId=0 当作 MCU 卡死的判据、把 USB 重枚举后偶尔出现的
4817 当作「短暂救活」，属于误读：`WalleCommon::mVendor` 是进程内缓存，vrhandle 常驻
进程曾成功过所以打印 4817/4222，launcherx 冷启动从未成功所以恒 0。

### 7.3 为什么 `ioGetVendorInfo` 必然失败：节点指错了

现场枚举（`/sys/class/hidraw/*/device/uevent` + `report_descriptor`）：

| 节点 | HID_ID / 名字 | 描述符前 16B | report 1 |
|---|---|---|---|
| `hidraw0` | `12d1:1092` HUAWEI GLASS **CV10** | `06 ff 00 09 01 a1 01 85 01 09 07 75 08 95 01 81` | **仅 1 字节** |
| `hidraw1` | `12d1:107e` HUAWEI GLASS HID (input3) | `06 ff 00 09 01 a1 01 85 01 09 07 75 08 95 3b 81` | **59 字节 IMU**，另有 report 4 = 127B feature |
| `hidraw2` | `12d1:107e` Consumer Control | `05 0c ...` | 按键口 |

`docs/HELMET_HID_PROTOCOL.md` 已定死协议：`ioGetVendorInfo()` = `HIDIOCGFEATURE(4)`
（`0xC0044807`），`buf[0]=1`，取 4 字节。发到 `hidraw0`（report 1 只有 1 字节）必然
被 hidraw/设备拒绝；`hidraw1` 才有能力应答。而 `WalleDev.cpp` 里 `/dev/%s` + `hwvr1`
证明 SDK 打开的就是 `/dev/hwvr1`。

**守护 bug**：`fix/magisk-module/modules/service.sh:115-119` 用「描述符前 3 字节 ==
`06ff00`」+ `break` 选第一个匹配。hidraw0 和 hidraw1 **前 3 字节完全相同**，于是永远
选中 hidraw0。脚本注释里写的「控制接口 (12d1:107e input3)，report 1 是 59 字节 IMU」
描述的其实是 hidraw1 —— 判据与意图自相矛盾。守护每 3 秒把链接改回 hidraw0，
所以任何手工改 symlink 都会被打回（实测 02:49:42 / 02:56:09 各一次）。

### 7.4 决定性 A/B 实验

| 实验 | 操作 | `ioGetVendorInfo failed` | `dev_open(886)` 失败 | `openDevice` vendorId | 结果 |
|---|---|---|---|---|---|
| 1 基线 | 直接 `am start` | 46（launcherx）+ 110（vrhandle） | 46 | 0 / 0 | 退出，栈顶回退 |
| A | `am force-stop com.huawei.vrhandle` 后重启桌面 | 156 | 46 | 0 / 0 | 仍退出；vrhandle 被自动拉起 → **排除「hidraw 进程竞争」** |
| B | 冻结守护（PID 408，`kill -STOP`，不改文件）→ `hwvr1 -> hidraw1` → 重启桌面 | **0** | **0** | **4817 / 4222** | `use helmet 2.0`、WalleAlg 加载成功、`isApiInitFlag=1`，但 Unity 仍退出 |
| D | B + 先重启 `ArvrRuntimeService` 再启动桌面 | 0 | 0 | — | 20 秒窗口栈顶稳定 `.MainActivity`、`OnApplicationQuit=0`；守护恢复后 symlink 被改回 hidraw0，桌面再次退出 |

实验 B 暴露**第二道闸**：

```
W HvrSdkBridge: vr_system_state binder not published yet
I UnityPlugin: CheckVrMode, dev is helmet, try to get VRMode
I UnityPlugin: CheckVrMode, is not VRMode, exit
E Unity_HVRRenderMgrCore: CheckVRMode FAIL, SDK Quit
E Unity_HVRRenderMgrCore: HVR Error, Current mode is not VRMode, ApplicationQuit
I VrFramework: finish all activity finish begin → 进程被杀
```

即 `dev_open` 修好后，兼容层的 `vr_system_state` binder 未发布（反复 `force-stop
launcherx` 会连带杀掉 `com.huawei.vrlauncherx.registry` ContentProvider 里的注册表，
而 `HvrStatePublisher` 只在 Runtime 服务启动时发一次，不会重发）→ `getVRModeState`
拿不到 → 判为非 VRMode → SDK 主动退出。实验 D 先重启 `ArvrRuntimeService` 让它重新
发布，桌面即驻留；守护把 symlink 改回 hidraw0 后又退出，反向印证第一道闸。

另：`DeviceServices` 启动 `com.sparkfox.sportsdeviceserver/.ActivityToStartService` 报
`error start`（该包已不存在）出现在退出前约 1.4 秒，但它只是 `W` 级「error start」，
未参与 finish 链，与第五章判断一致，仍排除。

### 7.5 修复方向（按优先级）

1. **改判据（治本）**：`service.sh` 遍历所有 `06ff00` 候选，取 `report_descriptor`
   **字节数最大**者（控制接口含 59B IMU + 127B feature，CV10 只有 27B），不要 `break`
   第一个。更贴合 `docs/HELMET_HID_PROTOCOL.md` 第 3 条的做法是恢复
   `hwvr-probe` 的「真发一次 `HIDIOCGFEATURE(4)`，谁应答谁就是控制接口」判据 ——
   `ksu/hwvr_compat/hwvr-probe.c` 已实现（`r == 4 ? 0 : 4`），需复核当时为何判
   「hidraw0/1 都返回 0」。注意 README 8.1 关于「前 3 字节即可识别」的表述要同步改。
2. **启动顺序**：守护状态机拉桌面之前，确认 `ArvrRuntimeService` 已起且
   `vr_system_state` 已发布；或让 `HvrStatePublisher` 在注册表重建时重发 binder
   （改 `shared/runtime-actor/java/com/huawei/hvrsdkserverapp/compat/HvrStatePublisher.java`）。
3. **临时验证命令**（不改任何文件，守护冻结期间有效）：
   ```sh
   adb -s 192.168.43.133:5555 shell su -c '
     kill -STOP $(pidof -s busybox)   # 实为 service.sh 的 PID，用 ps 确认
     rm -f /dev/hwvr1; ln -s /dev/hidraw1 /dev/hwvr1'
   adb -s 192.168.43.133:5555 shell am force-stop com.huawei.vrlauncherx
   adb -s 192.168.43.133:5555 shell am force-stop com.huawei.hvrsdkserverapp
   adb -s 192.168.43.133:5555 shell am start-service -n \
     com.huawei.hvrsdkserverapp/com.huawei.hvrsdkserverapp.service.ArvrRuntimeService
   sleep 5
   adb -s 192.168.43.133:5555 shell am start -n com.huawei.vrlauncherx/.MainActivity
   # 结束务必 kill -CONT 恢复守护
   ```
4. **不需要**：物理拔插眼镜 USB、MCU 断电复位、USB unbind/bind 自动重枚举（4.5 节
   第 3 条）、vrhandle/launcher hidraw 竞争排查（实验 A 已排除）。

## 十一、6DoF / 3DoF 识别链复核 + 「应用打不开」（2026-11-08 傍晚）

### 11.1 触发与纠正

用户报「ALVR 在 VR 桌面无法打开，其他软件也打不开」，随后指出
**HUAWEI CF20 是 3DoF 手柄**，要求回 `系统/` 核对原厂怎么识别 6DoF。
核对后**推翻本轮中途的两个误判**：

| 中途判断 | 纠正 |
|---|---|
| `Huawei 6Dof left/right/Header is false` = 6DoF 手柄未连接 | 错。这句判的是 **6DoF 视觉定位套件的设备表**，与 CF20 手柄毫无关系；本机常年 false，手册 8.3 已定性为 3DoF 眼镜的既有分支噪声 |
| `Controller Disconnected` + 蓝牙 DISCONNECTED = CF20 手柄掉线 | 只是 05:16 的短暂窗口；**05:24:35 已 `CONNECTED`**、`device is already connected`、`Controller Disconnected=0` |

### 11.2 原厂怎么识别 6DoF（`系统/` + 反编译实证）

`系统/` 为 EMUI 11 固件解包（`VRServiceX.apk`、`hid.jar`、
`SENSORHUB.img`、`libhivrar_service.so`、`vendor.huawei.hardware.hivrar@2.x.so`、
`hivrarserver.rc`）。逐文件扫字符串：这些 HAL/so 里 **没有
`6DoF` / `3DoF` / `CF20` 字面量**；`VRServiceX.apk` 只有安装/升级逻辑
（`CableActivity`、固件版本查询）。说明 **6DoF 判定不在系统 HAL，而在上层
`hvrsdkserverapp` / vrframework 的 Java 层**。

核心判据 `VrParamsRequester.isHW6DoFAvailable(I)Z`（smali 162-235 行）：

```java
if (mRuntimeInterface == null) return false;          // 日志 "mRuntimeInterface == null"
List<DeviceInfo> d = mRuntimeInterface.getCurrentDevices();
if (d == null || d.size() != 3) return false;         // 必须正好 3 个：头 + 左 + 右
return d.get(index).getDeviceState() == 1;
```

调用点：`isHW6DoFCtrlAvailable()` 用 index 1/2（左右都 true 才 true），
`isHW6DoFHeaderAvailable()` 用 index 0。绑定走
`bindRuntimeService()` → action
`com.huawei.hvrsdkserverapp.service.ACTION_GET_INTERNAL_INTERFACE`，
`ArvrRuntimeService.onBind()` 校验
`com.huawei.hvrsdkserverapp.permission.RUNTIME_ALLOW` 后返回内部 binder。

设备表来源（与 `docs/6DoF-为什么没起来.md` 对齐）：
`12d1:3a09` 双目 UVC → `class 0e/02` VideoStreaming → `/dev/video14/15`
→ HiVRAR HAL → VIO 位姿 → `getCurrentDevices()`。
**不是按 VID/PID、不是蓝牙**；`hvrsdkserverapp` 里没有 `BluetoothGatt`。

**3DoF CF20 是另一条链**：`com.huawei.vrhandle` 按 BLE 广播名
`contains("CF20_3DOF")` + 私有 GATT `622f5b2a` / `ffb4a651` 识别，
入库 `sp_device_storage.xml`（见 README 第九章 AutoScanCompat）。

### 13.1 先纠正取证方法上的两个坑

- **adb `am start` 触发不了 `B()`**。`HvrDisplayRouter.applyVrDisplay()` 在
  全部反编译产物里只被桌面 `z0/c.B(Context, Class)` 调用
  （`build/tmp/ctxa/dexdump/smali1/z0/c.smali:117`），而 `B()` 的调用者是
  `MainActivity` / `Vr2dStartUpActivity` / `PrivacyStatementActivity` /
  `VRPrepareActivity` 等桌面内部页面。用 adb 直接 `am start` 一个应用包
  **不经过桌面启动逻辑**（与 11.11 实测 `launchApp=0` 一致）；启动
  `MainActivity` 只是把已在前台的窗口提前，也不重走 `B()`。
  → 靠 adb 复现「打开应用」这条路本身就不成立，必须改从进程启动侧下手。
- **`grep -c "HUAWEI VR Display"` 会把 1 块数成 5 块**。`dumpsys display`
  里 `DisplayDeviceInfo` / `mUniqueId` / `mPrimaryDisplayDevice` /
  `mBaseDisplayInfo` / `mOverrideDisplayInfo` 都会出现同名字符串。
  体检脚本已改为只数 `DisplayDeviceInfo{"HUAWEI VR Display"` 行。

### 13.2 ① 到底断在哪：两个硬伤叠加

反编译 `build/tmp/glass_grace/smali/.../HvrDisplayRouter.smali` 与源码
`shared/java/.../HvrDisplayRouter.java` 逐条对照：

```java
int displayId = HvrVrVirtualDisplay.displayId();       // 本进程建过才算
if (displayId < 0) {
    Context context = ContextEx.currentApplication();
    if (context != null && HvrVrPanelPresenter.start(context)) {
        displayId = HvrVrVirtualDisplay.displayId();   // surface 还没回调，仍是 -1
    }
}
```

1. **Context 短路**：现场日志
   `HvrServiceManagerEx: no application context; vr_system stays process-local`
   证明 `ContextEx.currentApplication()` 确实可能为 null。此时
   `start()` 一次都不会被调用 —— 这正好解释第十二章「`HvrVrPanel` 全库 0 条」：
   `start(context == null)` 是唯一不打任何日志的返回路径。
2. **异步竞态**：即便 `start()` 成功，`Presentation.show()` 之后
   `SurfaceView.surfaceCreated` 是主线程异步回调，同一次 `applyVrDisplay()`
   里 `displayId()` 必然还是 -1，于是打印 `not up yet`、应用落到
   `displayId=0`。由于 `applyVrDisplay()` 只在「打开页面」时被调用，
   用户每点一次图标都在「第一次」，永远等不到屏建好的那一次。

### 13.3 修法与归属推导

`fix/patches/vrdesktop/fix_panel_bootstrap.py` 只改 launcherx 的
`classes4.dex` 中 `HvrContextProvider.onCreate()`。选择这个点的理由：

- ContentProvider 由平台在进程启动时实例化，`getContext()` **保证非 null**，
  且此前已先执行 `ContextEx.setApplication(context)`；彻底绕开硬伤 1。
- 只对 `com.huawei.vrlauncherx` 进程调用 `HvrVrPanelPresenter.start()`，
  因为 `z0/c.B()` 发起 `setLaunchDisplayId` 的也是这个 uid。
- 建屏前移到进程启动，`surfaceCreated` 有充足时间异步完成，硬伤 2 消失。

补丁在 `onCreate()` 的 `startVrEnvironment()` 之后插入一次
`maybeStartVrPanel(v0)`，新增的静态方法做包名判断 + try/catch，不碰原版
任何业务逻辑；幂等标记 `panel-bootstrap`。

**关键推论**：`HvrVrVirtualDisplay` 的头注释写过，
`isCallerAllowedToLaunchOnDisplay` 只放行「屏的拥有者本人」或 signature 级
特权；第十二章因此把 LSPosed 当成必需前置。但只要屏由**启动方自己**创建，
owner uid == 调用方 uid，根本不需要 trusted display，也就不需要 LSPosed。
LSPosed 模块 `com.hvr.displayrouting` 只对「Runtime 建屏、别的进程启动」
那条跨进程路径才是必需的。

## 十四、眼镜不点亮与 6DoF 激活链：一个循环依赖（2026-11-08 第六轮）

用户三连问：「眼镜是黑屏」「改用面具插件不行吗」「6DoF 手柄是不是需要
激活指令」。本轮把显示链之外的 USB 激活链与 6DoF 链一起复核，结论是
**三者指向同一个 SDK 内部循环依赖**，而不是权限、binder 或框架缺失。

### 14.1 现场：硬件与面具模块全通，激活指令为零

用户拔插电源重上电后，眼镜 USB 完整枚举（这次不再是 13 章取证时的
「只剩 4 个 root hub」）：

```text
hidraw0  06ff00 28B  12d1:1092  HUAWEI GLASS CV10
hidraw1  06ff00 68B  12d1:107e  HUAWEI GLASS HID     ← 控制口
hidraw2  050c09 39B  12d1:107e
hidraw3  06ffa0 53B  12d1:3a09  6DoF Gaming Kit Par-CG012
hidraw4  050109 59B  2109:8888
/dev/hwvr1 -> /dev/hidraw1 (descLen=68)   ← 守护选点正确
video14 / video15 (6DoF) 666、ttyUSB0-2 666
HDMI-A-1 connected，首选 3200x1600，resolution_white.xml 含 3200
HUAWEI VR Display 3200x1600 自动重建成功（13 章补丁持久有效）
```

即 Magisk 模块 `post-fs-data.sh`（EDID / 白名单 / 平台伪装）与
`service.sh`（权限 / 选点 / state / 拉服务）**每一环都生效**。
但 14 秒观测窗口内计数全为 0：

```text
active device : 0      ioGetVendorInfo : 0      HIDIOCSFEATURE : 0
mManager == null : 0   NO VR permission : 0     Not in Vr Mode : 0
Huawei 6Dof Header is false / left & right controller is false  ← 持续刷屏
```

**眼镜点亮的激活链**（`service.sh` 109-118 行注释、手册 4.3）：

```text
/dev/hwvr1(控制口) → libWalleDev.ioGetVendorInfo(): HIDIOCGFEATURE(4)/report 1
  → 激活命令 HIDIOCSFEATURE(5) → "active device(2) OK" → 面板点亮
```

节点是对的，但指令一次都没发。所以黑屏不是 EDID、分辨率、节点指向或权限
问题；现场应急按手册 4.3：眼镜有粘性激活态，失活后先用 PC/手机点亮一次
再插回盒子。

### 14.2 6DoF 的旧结论逐条证伪

第十一章把 6DoF 归到「`ACTION_GET_INTERNAL_INTERFACE` binder 缺口 /
`RUNTIME_ALLOW` 权限」。反编译 + 现场逐条核对后修正：

| 项 | 结论 | 证据 |
|---|---|---|
| `onBind` 权限 | 校验的是 **`com.huawei.android.permission.VR`**，且 `granted=true` | `ArvrRuntimeService.smali` 248-252；`dumpsys package` |
| `RUNTIME_ALLOW` | `granted=true` | `dumpsys package` |
| `checkCallingOrSelfPermission` | 服务端自己也持有 → 恒放行 | 语义「调用方或自己」 |
| `isVrMode` 三处判断 | `onCreate` / `onBind` / `onStartCommand` **全部已 patch 成常量 true** | 设备上 pull 的 `classes.dex` 反编译，438/618/964 行 |
| `vr_system` | 注册表里已有 `binder=BinderProxy` | `content call ... getService vr_system` |
| `isVRMode` | `HvrSdkBridge: getVRModeState -> 1 isVRMode=true` | logcat |
| 绑定 | `dumpsys activity services` 有 `ACTION_GET_INTERNAL_INTERFACE` 的 `ConnectionRecord`，binding 来自 `com.huawei.vrlauncherx`；`bind RuntimeService suc.`、`ArvrRuntimeService: onBind` 均出现 | 重启 Runtime 后的 A/B |
| `VrFrameworkBootstrap` | `framework=true helmet=false`，`VrFramework.init` 已执行 | `HVRActivity.onCreate` 已注入 `VrFrameworkBootstrap.init(this)` |
| 仍失败 | `mRuntimeInterface == null`、`runtimeBinder is null` | `VrParamsRequester` / `6dof_VrCommon_VrRuntimeUtil` |

**「只 patch 了 onBind 一半」的假设也被证伪**：设备上三处 `isVrMode`
都已改成常量 true。曾尝试 A/B（`am force-stop hvrsdkserverapp` →
`start-service` → 重启桌面），`onBind` 从 0 次变成 2 次，但
`mRuntimeInterface` 仍为 null。

### 14.3 真正的断点：`VrHelmetExt` 循环依赖

反编译 `VrHelmetExt.smali`：

```java
public boolean isEnable() {
    if (vrService == null) vrService = VRSystemServiceManagerImpl.get(mActivity);
    if (mVRDeviceExt == null) {
        // 只有 6DoF 头显可用时才创建设备管理器
        if (VrFramework.isHW6DoFHeaderAvailable()) { mVRDeviceExt = ...; }
    }
    return mVRDeviceExt != null;
}
```

而 `isHW6DoFHeaderAvailable()` → `VrParamsRequester.isHW6DoFAvailable(0)`
→ 第一行 `if (mRuntimeInterface == null) return false`。于是：

```text
mRuntimeInterface == null
  → isHW6DoFAvailable(0) = false
  → VrHelmetExt.isEnable() 不创建 mVRDeviceExt
  → VrInteractiveDeviceManager 不初始化 → 激活指令不发
     （ArvrRuntimeModuleManager.updateHandleLight → updateHandleLightNative
      也在同一条 manager 链上）
  → 眼镜面板不点亮、6DoF 头/左/右设备不上报
  → getCurrentDevices() 为空 → mRuntimeInterface 继续 null
```

现场每帧刷 `VrHelmetExt: mVRDeviceExt is null` 正是这个死锁的指纹。
**6DoF 手柄确实需要激活/上报链路，但它和眼镜点亮是同一个上游，不是一条
独立的「手柄激活指令」**。打破死锁需要 patch `hvrframework.dex` 的
`VrHelmetExt.isEnable()`（让 `mVRDeviceExt` 不依赖 6DoF 判定即可创建），
或先让 `onBind` 返回的 binder 有效。这属于 SDK 内部 Java/native 逻辑。

### 14.4 面具插件的能力边界（回答「改用面具插件不行吗」）

| 层 | 能做 | 本轮结论 |
|---|---|---|
| Magisk `post-fs-data.sh` | EDID、HWC 白名单、ro 属性伪装 | 全部生效，黑屏与它无关 |
| Magisk `service.sh` | 节点权限、hwvr1 选点、state、拉服务 | 全部生效 |
| Java 方法 hook（Zygisk / LSPosed） | `isCallerAllowedToLaunchOnDisplay` 等 | **显示路由已不需要**（13 章同 uid 建屏）；6DoF 也不是 hook 能解的 |
| SDK 内部循环依赖 | 需 patch `hvrframework.dex` | Magisk 与 LSPosed 都不对症 |

结论：**面具插件该做的都做了且生效，不需要改装 LSPosed。**

本轮给 `service.sh` 补了「无线 adb 5555 自愈」：`wadb` 模块只在开机做
10 次有限重拉就退出，运行时 adbd TCP 监听丢失即永久失联。hvrglass 是唯一
常驻循环，现每 60 秒检查一次、端口确实没监听才 `ctl.stop/start adbd`；
`touch /data/adb/hvrglass/wadb_guard_off` 可关闭。已 root 部署到
`/data/adb/modules/hvrglass/service.sh`，下次重启生效。

> ⚠️ 禁令：本轮做过一次自动回滚的 A/B，
> `setprop sys.usb.config none` **立刻打断唯一无线 adb 通道**
> （ping 0% 丢包、5555 拒绝连接、wadb/守护均未自愈，最终由用户拔插电源
> 恢复）。`/sys/class/udc` 空 + `sys.usb.controller` 空造成的 gadget 配置
> 残缺，目前没有软件侧安全修法，只能现场查线缆 / Type-C 转接 / hub 供电。
> 不要再拿唯一调试通道做这类实验。该结论已写进 `service.sh` 注释。
