# 刷机后问题分析与恢复手册（2026-11-02 深夜）

> 本文回答三个问题：**为什么看起来"又搞坏了"**、**哪些问题是真问题**、**刷机完成后按什么顺序恢复**。

---

## 一、为什么"又搞坏了"——时间线复盘

今晚实际发生的事，按顺序：

1. **ALVR 无线串流已经打通**（22:40 前后）：眼镜里能看到串流画面，PC 端 `connection_state: Streaming`。这是真实成果，没有丢。
2. 为修"VR启动失败"（dlopen 缺库），更新了两个 APK + 模块加了两个文件，然后**重启盒子验证 Magisk 模块改动**。
3. 重启后盒子失联 —— **根因：刷机/重置会清掉 `adb tcpip 5555` 持久设置**，无线 adb 端口死了，只剩 ping 通。盒子本体没坏，是管理通道断了。
4. 上一次刷机后我们做过一轮全量重部署，但**又一次重启**后同样的问题再次出现。两次"失联"是同一个机制，不是新的损坏。

**结论：盒子没有物理性损坏。"搞坏了"的表现 = 无线 adb 丢失 + 重复刷机的累积返工。**

## 二、问题分类总账

### A 类：刷机必然清空（不是故障，但每次刷机都要重做）
| 项目 | 恢复方式 |
|---|---|
| 7 个 VR 包 + ALVR | `fix/install.sh` 一键装回（已含 sofix 版 + ALVR，共 8 包） |
| Magisk hvrglass 模块（EDID/伪装/hwvr1/库白名单） | install.sh 会部署，或手动推 `fix/magisk-module/` |

| **无线 adb** | **必须插 USB 线** → `adb tcpip 5555` → 拔线 |

1. **sharedUserId 不兼容** → 去 sharedUserId + 统一 hvr-compat 签名（8 包同签）。
2. **vrlauncherx 隐私页崩溃** → `settings put system PRIVACY_ACCEPTED 1`。
3. **himovie 自杀（root 检测）** → smali 恒 false。
4. **VR EDID / 普通屏黑屏冲突** → post-fs-data.sh 按需注入（mode=auto/force-vr/force-off）。
5. **VrMonitor.checkVRMode 强退** → `/dev/hwvr1` + 辅助显示器（三项检测错 1 项可过）。
6. **VrPlatformCompat 拿不到 context** → 反射兜底 + hwvr1 文件探测，已编进 hvrsdkserverapp-sofix（classes4.dex 与 assets/hvrframework.dex 双处确认在位）。
7. **ALVR 平台识别失败 ERROR_HANDLE_INVALID** → `resetprop ro.product.manufacturer HUAWEI`（post-fs-data.sh，zygote 前执行）。
8. **dlopen 缺 libc++/libstdc++/libc++_shared** → 打进 APK lib 目录（sofix）。
9. **dlopen 缺 libutils.so** → `public.libraries.txt` 白名单 + libc_secshared.so overlay（模块 system/ 目录）。

### C 类：未解的真问题（与刷机无关，一直存在）
1. **vr_system 服务不注册**：sharedUserId 移除后无人注册系统服务 → **vrlauncherx VR 桌面门禁永远拦截**（"请连接华为VR眼镜"）。只能 LSPosed 桩或绕开华为栈。ALVR 走"直接启动"旁路，不依赖此环节。
2. **composer HAL 咬死 1080p**：VOP 把 1920x1080 拉伸铺满 3200x1600 双目面板 → 眼镜看系统桌面是"左眼左半右眼右半"。正解是渲染端出 SBS（ALVR 已原生 SBS，所以串流画面正常）。
3. `/data/adb/hvrglass` 下 root 写入部分被拒（SELinux Permissive 仍拒，原因未明）。

### D 类：操作风险（这次和上次的教训）
- **每次重启前，先确认改动清单**：模块脚本 / resetprop / 设置项，逐条列给用户。
- **不要依赖"重启后自动恢复"**：tcpip 5555 一定会丢，重启 = 预约一次插线。
- post-fs-data.sh 追加内容会落在 `exit 0` 之后不执行（已修：伪装段在文件末尾 exit 0 之前）。

## 四、2026-11-03 凌晨新增：两条会让盒子"假死"的硬教训

### 4.1 开机注入 EDID = 卡 logo（三次启动对照实锤）

| 启动时刻 | `/data/adb/hvrglass/mode` | 眼镜 | 结果 |
|---|---|---|---|
| 00:30 | 无（默认 auto，不注入） | 未接 | ✅ 正常进系统 |
| 01:15 | **force-vr（开机注入）** | 已接 | ❌ 卡 logo |
| 06:00 | force-vr（文件持久，仍注入） | 已接 | ❌ 卡 logo |

**根因**：post-fs-data 阶段写 `edid_override` 会让内核重解析 EDID 并重建显示模式，而此时 HWC/SurfaceFlinger 尚未就绪，本盒子的 DRM/HWC 在这个窗口会死锁，bootanimation 永远停住。

**结论：永远不要在开机阶段注入 EDID。** 正确做法见 4.3。

### 4.2 `setprop ctl.restart surfaceflinger` = 盒子直接重启/卡死

实测两次：执行后 adb 立刻断开，1 分钟后才回来（其中一次 uptime 归零 = 整机重启）。
`edid-mode.sh` 已改为**不再调用**该命令，改用拔插 HDMI（HPD 上升沿）让内核重读 EDID。

### 4.3 眼镜点亮的正确姿势（不要重启）

```
1) sh /data/adb/hvrglass/edid-mode.sh vr      # 只写 override，不动 SF
2) 物理拔插一次眼镜的 HDMI（等 3 秒再插回）
3) 验证: head -6 /sys/kernel/debug/dri/0/summary  应出现 3200x1600p70
```

配套硬结论（来自 PLAYBOX 排障手册实机验证）：
- **眼镜没有 scaler，只吃原生 3200x1600**；输出 1080p 必黑，别试低分辨率。
- **眼镜有"激活"状态且粘性**：在 PC 上点亮过一次、再插回盒子就会亮。若拔插后仍黑，先用 PC 点亮一次再插回。
- **EDID 读到 ≠ 能点亮**：还要 HWC 白名单放行 3200x1600，见第六章（2026-11-04 实锤）。

### 4.4 post-fs-data.sh 的一个真 bug（已修）

原脚本 `force-vr` 分支写完 EDID 就 `exit 0`，导致后面的 `resetprop ro.product.manufacturer HUAWEI`
和 `touch /dev/hwvr1` **永不执行**（表现为"伪装莫名丢失"，ALVR 报 ERROR_HANDLE_INVALID）。
现已改为：**伪装与 hwvr1 无条件最先执行**，EDID 分支只负责写文件、不再提前退出。

## 六、2026-11-04 里程碑：眼镜 HDMI 原生点亮（HWC 白名单 + 内核真值）

> 状态：**成功**。VOP 实际输出 `3200x1600p70, clk[412180]`，眼镜点亮。
> 持久化：白名单 bind mount 已写进 `post-fs-data.sh`（module hvrglass）。

### 6.1 根因链（为什么之前永远 1080p）

眼镜 EDID 其实能读上来（厂商 ID `HWV`，含 3200x1600@70/90 两条 DTD），卡点在 HWC：

1. **`/system/usr/share/resolution_white.xml` 白名单过滤**：`hwcomposer.rk30board.so` 的
   `DrmConnector::mode_verify` 只放行白名单里列出的模式（比较 clock/hdisplay/vdisplay/
   htotal/vtotal/flags 六字段）。原厂白名单 54 条全是 CEA 标准模式，**没有 3200x1600**
   → 3200 模式根本进不了 HWC 模式表 → `Find best mode` 永远回落 1080p60。
2. **就算加了条目，vsync 字段手算必错**：白名单条目要求与内核解析出的 `drm_display_mode`
   全字段相等（`DrmMode::eq` 比 10 个时序字段）。EDID DTD 的 vsync 字段按 spec 手算出
   2065/2068，而 4.19 内核实际解析出 1629/1630（内核公式与直觉不同）→ eq 匹配失败。
3. `/system` 剩余空间不足 5MB，直接改白名单文件会 `No space left on device` 且把原文件
   截断成 0 字节 → 必须走 /data + bind mount（systemless）。

### 6.2 解决方案（三步）

**① 用 `tools/modeinfo.c` 读内核真值**（NDK 静态编译，裸 ioctl DRM_IOCTL_MODE_GETCONNECTOR）：

```
NDK 编译: aarch64-linux-android29-clang -static -O2 -o modeinfo tools/modeinfo.c
设备运行: /data/local/tmp/modeinfo
```

输出 HDMI-A-1 全部模式及内核解析值。本次实测真值：

| 模式 | clock(kHz) | h(v) 序列 | vrefresh | flags |
|---|---|---|---|---|
| 3200x1600@90 | 529940 | 3200/3260/3268/3308 · 1600/1629/1630/1780 | 90 | 0x5 |
| 3200x1600@70 | 412180 | 同上，但 v=1600/1663/1664/1780 | 70 | 0x5 |

**② 按真值重写白名单条目**，拼进 `/data/adb/hvrglass/resolution_white.xml`
（原白名单去掉 `</resolutions>` 尾标签 + 追加两条 + 补回尾标签），bind mount：

```
mount -o bind /data/adb/hvrglass/resolution_white.xml /system/usr/share/resolution_white.xml
```

**③ 重启 SurfaceFlinger 让 HWC 重读白名单**（用 `stop; start`，**绝不用** `ctl.restart`，见 4.2）：

```
stop surfaceflinger; sleep 2; start surfaceflinger
```

验证：`logcat -d -s hwc-drm-connector` 出现 `Find best mode-id=4 : 3200x1600p70.000000`；
`head -6 /sys/kernel/debug/dri/0/summary` 出现 `clk[412180]`。

### 6.3 关键坑位备忘

- **白名单 bind mount 换的是 inode**：mount 之后必须重启 HWC/SF 才生效，热插拔 HPD 不够。
- **`/proc/<hwc_pid>/root/...` 可验证 HWC namespace 视角**：bind mount 后 HWC（独立进程
  `vendor.hwcomposer-2-1`）能看到新文件，namespace 不是问题。
- **`echo detect > status` 可触发 HWC UpdateModes**，但选模式结果仍受白名单限制。
- **`mode=force-vr` 别固化**（4.1 卡 logo 教训），现保持 `mode=auto`：能读到真实 EDID
  （HWV）就直通，读不到才注入。
- 每次改白名单前先 `cp ... /data/local/tmp/resolution_white.xml.bak`——写入失败会把原文件截断。
- /system 写不进 ≠ df 显示有空间；老 ext4 预留 + inode 情况，直接走 /data bind mount。

### 6.6 2026-11-05：固化成一键点亮工具（本次复现成功）

**背景**：11-04 晚加的开机自愈（detect 重探 / 强制属性 / 自动重启 HWC）造成崩循环，

稳定，没再出现「一进系统就关机」。不亮的直接原因只有一条：上次「属性复位」把

**三步（与 11-03 10:37:56 的历史成功记录逐项一致，18:10 再次实测成功）**：

## 6.7 救砖后别忘了「重新启用模块」+ VR 服务链三件套（2026-11-05 实证）

卡 logo 时跑过 `rescue_boot.sh --disable-hvrglass` 的设备，会留下
`/data/adb/modules/hvrglass/disable`。**这个标记不会随刷机/重装自动消失**，
之后模块整套不执行，症状极易误判成「软件又坏了」：

| 缺失项 | 表现 |
|---|---|
| `resetprop ro.product.manufacturer HUAWEI` | 仍是 rockchip，部分华为包判定机型失败 |
| `resetprop ro.vr.surport true` | 投屏弹「当前系统版本或机型不支持打开该应用」 |
| 开机白名单 bind mount | 回落 1920x1080p60、眼镜黑屏 |
| `service.sh` hidraw 守护 | `/dev/hidraw*` 停在 `660 system:audio`，ALVR 拿不到 IMU |
| `service.sh` VR 服务开机自启 | VRService / ArvrRuntimeService 全空 |

排查一行命令：

```sh
adb shell su -c 'test -f /data/adb/modules/hvrglass/disable && echo DISABLED || echo enabled'
```

恢复（运行时即可，不必改脚本）：

```sh
adb shell su -c 'rm -f /data/adb/modules/hvrglass/disable; \
  resetprop ro.product.manufacturer HUAWEI; resetprop ro.vr.surport true'
```

`fix/install.sh` 的第 4 步现在会自动做这三件事；**模块在下次重启后才会真正生效**。

### VR 服务链的三个硬前提

1. **deviceidle 白名单**（Android 11 BAL，连 root 的 `am start-service` 都拦）：

### 图形栈僵死的唯一解法

若 `am start` 连 `com.android.settings` 都抛
`android.view.Surface$OutOfResourcesException`
（`Task.setInitialSurfaceControlProperties`），说明图形会话已僵死，
**任何新 Activity 都起不来**，ALVR / 投屏 / VR 桌面此时都验不了。

按 11-03 的结论：**只能干净重启，且重启时眼镜 HDMI + USB 都保持插着**，
让 HWC 在「已连接」状态下初始化。不要试图运行时 `stop/start surfaceflinger`
或重启 HWC —— 那正是制造僵死的动作。重启前确认
`wadb` 模块 ENABLED + `persist.adb.tcp.port=5555`，否则会失联。

### 6.7.1 开机后立刻重启 SF 的时序坑（2026-11-05 23:00 两次实测）

干净重启能修好僵死，但**开机阶段属性与白名单虽已就位，HWC 仍可能选
1920x1080p60** —— HWC 首次 probe 早于 persist 属性 / bind mount 生效的时机。
此时若急着跑点亮脚本的第 ③ 步：

- `stop; sleep 2; start surfaceflinger` 确实能在 5 秒内切到 `3200x1600p70`；
- 但开机后几分钟内 system_server 会被这次 SF 重启带崩，触发**整机重启**，
  重启后又回 1080p。上午成功那次是系统已连续稳定运行数小时。

所以：**不要在系统刚开机时反复试 SF 重启**。要么等 uptime ≥10 分钟再手工一次，
要么改从根上解决「HWC 开机即选 3200」（让白名单/属性在 HWC 初始化前就位）。

### 6.7.2 light-on.sh 误删属性的修复

旧版第 ③ 步之后固定 `sleep 10` 就判定，失败即 `del_prop` 删掉两个
`persist.vendor.resolution.*`。整机重启窗口里必然读到旧值 → 误判 →
**把刚写好的成功配置删掉**，重启后只能回落 1080p。

2026-11-05 已修（`fix/magisk-module/runtime/light-on.sh`）：

1. 验收改成最多 90 秒轮询，出现 `3200x1600p70` 立即成功；期间绝不删属性。
2. 失败时**只在眼镜明确失活**（`status != connected` 或模式表无 3200）才回滚；
   眼镜在位、模式表含 3200 时保留 persist 属性，供下次开机 probe。
   眼镜没醒时 HWC 只是回落 1080p，不会崩，保留属性的风险远低于删掉。

本地入口 `fix/light-on.sh` 每次会按 md5 自动把新版同步到设备，
也可手动 push 到 `/data/adb/hvrglass/light-on.sh`。

### 6.8 「开机即 3200」为什么做不到（2026-11-05 代码级实锤）

**结论：HWC 只在自身进程初始化时调用一次 `UpdateDisplayMode`，开机之后
没有任何温和手段能让它重选模式。** 这不是属性没设对，也不是白名单没挂。

证据链（本轮从设备 so 与 logcat 直接取到，不是推测）：

1. `/vendor/lib64/hw/hwcomposer.rk30board.so` 里有
   `DrmDevice::init_white_modes()`、`/system/usr/share/resolution_white.xml`、
   `display=%d persist.vendor.resolution.%s=%s`、`resolution_value=%s`、
   `can't find suitable Resolution Property, try to use Baseparameter`、
   `Find best mode-id=%d : %dx%d%c%f` —— 白名单与属性都在初始化期读取。
2. 本次开机日志（HWC PID 216）：
   ```
   UpdateDisplayMode,line=332  persist.vendor.resolution.HDMI-A-0=3200x1600@70
   UpdateDisplayMode,line=346  resolution_value=3200x1600@70
   UpdateDisplayMode,line=439  Find best mode-id=19 : 1920x1080p60
   GetFramebufferInfo,line=730 persist.vendor.framebuffer.main=1920x1080@60
   ```
   属性完全正确、白名单 `SYS3200=2`，仍走 line=439 fallback 选 1080p ——
   因为**那一刻模式表里没有 3200**（眼镜 EDID 比 HWC probe 晚几秒才就绪）。
3. 历史成功 `11-03 10:37:56` 是 **HWC 新进程 PID 23020** 重新初始化时
   `UpdateDisplayMode,line=385, Find best mode-id=4 : 3200x1600p70`；
   开机初始 HWC（PID 217）在 `09:18` 属性已是 3200 却选 `1280x720p60`，
   `09:58`（PID 4834）选 `1920x1080p60` —— 全部是同一模式：模式表当时无 3200。

**本轮新增的证伪（都是在系统已稳定、眼镜醒着、白名单在位、模式表有 3200 的情况下）**：

| 尝试 | 结果 |
|---|---|
| `delprop` → `setprop` 两个 resolution 属性，制造属性变化事件 | 30 秒无变化，HWC 日志无新增 `UpdateDisplayMode` |
| `setprop sys.resolution.changed true` | 无变化 |
| 单次 `echo detect > /sys/class/drm/card0-HDMI-A-1/status` | 40 秒无变化；系统健康、未重启、眼镜仍 `22f6`、3200 模式 2 条 |

**为什么不能靠重启 HWC**：`/vendor/etc/init/android.hardware.graphics.composer@2.1-service.rc`
里有 `onrestart restart surfaceflinger` —— 重启 HWC 等于重启 SF，正是 6.7.1
实测会带崩 system_server 的路径。

**剩下的唯一根治方向（都需用户明确同意，风险高，本轮未执行）**：

- 改 `/vendor/etc/init/hw/init.mount_all.rc` 里 `start hwcomposer-2-1` 的时序，
  让 HWC 在眼镜 EDID 就绪后初始化；或
- 开机早期写 `edid_override`（**违反 4.1：三次实锤卡 logo**）。若真要试，
  母本必须换成真实 `22f6` EDID：现用 `common/edid_only.bin` 是 `22d2`、
  只有 1 条 DTD、与真实眼镜差 93 字节；`.tmp-edid/edid_live.bin`
  与设备当前读到的真实 EDID **逐字节一致**（md5 `eba6de4e…`，2 条 DTD）。

在此之前，「开机后一键点亮」仍走第六章三步；**不要再重复试 detect /
属性变化 / 开机注入**，也不要在开机后几分钟内反复重启 SF。

### 6.10 "做 A" 实测：补 ctx1 证伪，根因比 64.4 更深（2026-11-05 23:4x）

用户授权后按最小差分做了完整一轮，**已全量回退**，设备回到动手前稳态
（vrservice PID 常驻、ClassNotFound 崩溃数 0、uptime 未重置）。

构建手法（可复用，比 apktool 全量重建安全）：
- 以**设备上正在运行的 base.apk** 为基线（`adb pull`，md5 核对），
  用 `patches/axml_edit.py` + `patch_context_provider_processes.patch_binary`
  只替换二进制 `AndroidManifest.xml`；
- 其余 1219 个条目**逐条保留 compress_type / external_attr / timestamp**
  （脚本会断言一条都没变），剔除 3 个旧签名条目；
- `zipalign -f -p 4` → `apksigner sign --ks fix/signing/hvr-compat-debug.jks
  --ks-key-alias hvrcompat --ks-pass pass:android`；
  证书 SHA-256 与设备基线一致 `30094ded91bf…814` → 可覆盖安装。
- 工具脚本：`build/tmp/ctxa/add_ctx1.py`、`add_ctx0_vrservice.py`。

**实测结论（三条硬事实）**：
1. 补进 launcherx 的 `ctx1`（authority `...hvrcompat.ctx1`、
   `process=com.huawei.vrservice`、`exported=false`）**成功注册**到系统权威列表，
   但 `vr_system stays process-local` 刷屏没停 —— 刷屏方是
   **uid 10073 / `com.huawei.vrservice` 包自己的默认进程**（v12.0.0.302），
   不是 launcherx 的子进程。
2. **launcherx 从原包到所有成品（含 11-04 的 68MB ctxfix）都不含
   `HvrContextProvider` 类**（全量扫 dex 确认，3 个 dex 全无）。
   它 manifest 里那个主 provider 声明是**空壳**。含该类的只有
   `hvrsdkserverapp`(classes4.dex) / `vrservice`(classes4.dex) /
   `vrvirtualscreen`(classes2.dex)。所以只要 launcherx 进程被启动
   （本轮由 `am start MainActivity` 触发），立刻
   `ClassNotFoundException: com.huawei.vrframework.compat.HvrContextProvider`
   → 进程崩溃循环。**补 ctx1 只会让子进程一起崩，A 的前提在这台盒子上不成立。**
3. `com.huawei.vrservice` 包里那个 provider 节点（authority
   `...hvrcompat.ctx`）在二进制 AXML 里的 **pos=56，而 `<application>` 起始
   pos=59** —— 挂在 `<application>` **之外**，PackageParser 直接忽略，
   设备上 `dumpsys package com.huawei.vrservice | grep hvrcompat` 为空。
   类明明在 `classes4.dex` 里却永远不实例化，这才是
   `ContextEx.application=null` 的直接原因。补一份位置正确的默认进程
   provider（`...ctx0`，pos=124 > 59）能注册成功，但当时被 launcherx
   的崩溃循环淹没，尚未单独验证 `vr_system` 是否发布。

**下一步的正确顺序**（不要再单补 launcherx）：
① 先让 launcherx 不再崩 —— 移除它那个空壳 provider 声明，或给 launcherx
   注入含 `HvrContextProvider` 的 compat dex（较大改动）；
② 再给 vrservice 包补位置正确的 provider（ctx0 产物已备好）；
③ 才验证 `published vr_system` / `helmet=true` / VR 桌面。
两个补丁 APK 与设备基线 APK 都留在 `build/tmp/ctxa/`，随时可装可退。

## 七、VR 桌面链路：崩溃循环根因与 2026-11-05 修复

用户口径「先解决进 VR 桌面问题，再解决 ALVR 启动问题」。本章是这条线的
完整取证与修法，**框架层已全部打通，原生层剩一处硬阻塞**。

### 7.1 根因链（真机日志，不是推测）

`com.huawei.vrlauncherx` 的清单在 `<application>` 内声明两个 provider，
但三个 dex 里这两个类**都不存在**（连原包也没有）：

```
com.huawei.vrframework.compat.HvrContextProvider          authority=.hvrcompat.ctx
com.huawei.vrlauncherx.compat.VrSystemRegistryProvider    authority=.registry
```

于是进程一启动就崩：

```
Process: com.huawei.vrlauncherx
java.lang.RuntimeException: Unable to get provider
  com.huawei.vrframework.compat.HvrContextProvider: ClassNotFoundException
→ Process com.huawei.vrlauncherx has crashed too many times: killing!
→ Killing com.huawei.vrservice: depends on provider
   com.huawei.vrlauncherx/.compat.VrSystemRegistryProvider in dying proc
→ Timeout waiting for provider com.huawei.vrlauncherx.registry
→ Canceling start item Intent {cmp=com.huawei.vrservice/.VRService}
```

**vrservice 是被 launcherx 的崩溃连带杀死的**，所以 `VRService` 永远起不来、
`vr_system` 永远 `process-local`、VR 桌面永远停在 `Vr2dStartUpActivity`。
之前 A 方案「只补 provider 声明」注定无效：补再多的声明也只是更多空壳。

第二处独立缺陷：`com.huawei.vrservice` 清单里那个 `HvrContextProvider`
节点 AXML pos=56，`<application>` pos=59 —— 挂在 application **外面**被
PackageParser 忽略（dumpsys 查不到 hvrcompat），类明明在 `classes4.dex`
却不实例化，`ContextEx.application` 恒为 null。Android 11 上
`ContextEx.currentApplication()` 的 `ActivityThread` 反射兜底被 hidden API 拦掉，
只能靠 provider 实例化时调 `ContextEx.setApplication()`。

### 7.2 修法：复用现成已编译 dex，不重新编译 Java

`com.huawei.vrservice` 的 `classes4.dex`（**仅 88KB**）里已经编译好全套
compat 类，逐字节核对含：

```
Lcom/huawei/vrframework/compat/HvrContextProvider;
Lcom/huawei/vrlauncherx/compat/VrSystemRegistryProvider;
Lcom/huawei/vrservice/compat/CompatAppContext;
Lcom/huawei/android/content/ContextEx;
```

所以只需把它作为 `classes4.dex` 追加进 launcherx（原有 3 个 dex），
两个悬空 provider 立刻有类，无需 apktool 全量重建。

三步最小差分（全部在 `build/tmp/ctxa/`，也已复制到 `fix/patches/vrdesktop/`）：

| 步骤 | 脚本 | 产物 |
| --- | --- | --- |
| ① 注入 compat dex | `inject_compat_dex.py` | `launcherx_compat_unsigned.apk` |
| ② 补子进程 ctx1 | `add_ctx1_compat.py` | `launcherx_full_unsigned.apk` |
| ③ zipalign -p 4 + apksigner | — | `launcherx_full_signed.apk` |
| ④ vrservice 补 ctx0 | `add_ctx0_vrservice.py` | `vrservice_ctx0_signed.apk` |

- `ctx1`：`android:process="com.huawei.vrservice"` → authority
  `com.huawei.vrlauncherx.hvrcompat.ctx1`。launcherx 的 VRService 客户端组件
  跑在这个子进程，不补就一直刷 `no application context`（PATCH_AUDIT 64.4）。
- `ctx0`：不带 process，落在 vrservice 包默认进程（正是刷屏那个进程）。
- 签名 `CN=HVR Offline`，SHA-256 `30094ded…814`，与设备基线一致，可覆盖安装；
  zipalign `-p 4` 保留；这版 launcherx 是 `extractNativeLibs=true`，
  `.so` 本来就是 DEFLATED，**不要**硬性要求 STORED（第一版脚本在此踩过坑）。

### 7.3 一键工具

`fix/一键修复VR框架.bat`（双击）/ `fix/一键修复VR框架.sh`，动作：
`install`（默认）/ `check` / `off` / `rollback` / `launcher`。

1. 覆盖装两个补丁 APK；
2. `su 10073 -c 'am start-service -n com.huawei.vrservice/.VRService'`
   —— **必须切到包自身 uid**：`VRService` 是 `exported=false`，shell(uid 2000)
   直接 `am start-service` 报 `Requires permission not exported from uid 10073`；
3. `settings put global overlay_display_devices 1920x1080/320`
   —— 用系统自带「模拟辅助显示」造出第二块 display。
   `VrPlatformCompat.isVrGlassPresent()` 要求「USB 身份 **且** 非默认 display」，

### 8.1 Java / 集成层补齐（按真实冷启动路径取证）

先坐实当前盒子走的不是 `LibUpdateServer.initJNIEnv()` 2.0 路径：

### 8.2 决定性根因：32 位 vrhandle 拿到 64 位 runtime 的库目录

修完上面 8 条后，30 秒冷启动日志里仍每 0.2~0.3 秒刷一个
`FATAL EXCEPTION: Binder:xxxxx_3`：

```
Process: com.huawei.vrhandle:VRHandleService
java.lang.UnsatisfiedLinkError: No implementation found for void
    com.huawei.vrhandle.VrPoseJni.helmetPoseStart()
  at com.huawei.vrhandle.service.VRHandleService.e3(VRHandleService.java:24)
  at com.huawei.vrhandle.g$a.onTransact(IVRHandleServiceAidl.java:55)
```

`docs/PATCH_AUDIT.md` 6.1 节早就记录过同一个崩溃（当时根因是 Android 11+
包可见性，已由 `<queries>` 修好）。这次重新取证发现**新的错位**：

- `VrPoseJni.<clinit>` 用 `r0.y0.j0()` 取
  `createPackageContext("com.huawei.hvrsdkserverapp", 3).getApplicationInfo().nativeLibraryDir`，
  再拼 4 个 `System.load(绝对路径)`：
  `libMobileSensor.so / libWalleAlg.so / libWalleDev.so / libvrpose.so`；
  `catch (UnsatisfiedLinkError)` 只打 `load library error` 就吞掉，于是 6 个
  native 方法全空，外部一问 `helmetPoseStart()` 就崩。
- 设备上 `com.huawei.vrhandle` 是 `primaryCpuAbi=armeabi-v7a`（32 位），
  而 `com.huawei.hvrsdkserverapp` 是 `primaryCpuAbi=arm64-v8a`（64 位）。
- runtime APK 里**同时**有 `lib/armeabi-v7a/`（29 个 ELF32）和
  `lib/arm64-v8a/`（30 个 ELF64），系统按 64 位只解压后者到 `lib/arm64/`，
  设备上 **`lib/arm/` 是空的**。实测 `lib/arm64/libvrpose.so` 与
  `libWalleDev.so` 的 `EI_CLASS=2`、`e_machine=183`（AArch64）。
- 于是 32 位进程拿到的 `nativeLibraryDir` 里全是 ELF64，加载必然失败。
  **这正是第 8.1 节第 1 步补 64 位库时被忽略的连带影响**；历史成功日志
  `.../lib/arm/libvrpose.so ... ok` 对应的是 runtime 为 32 位的旧安装。

修法（`fix/patches/vrdesktop/fix_vrhandle_pose.py`，只改一个包）：

1. 从 runtime APK 的 `lib/armeabi-v7a/` 解出依赖闭包所需的 4 个 ELF32 库
   （BFS 算过 `DT_NEEDED`：除这 4 个外全是 `libc/libm/liblog/libdl/libandroid`
   系统库，顺序加载即可满足），放进 vrhandle 的 `lib/armeabi-v7a/`，STORED；
2. binary AXML 把 `android:extractNativeLibs` 的 boolean data 从 `0x0`
   改成 `0xffffffff`（**只改 4 个字节**，不重建 AXML），让系统解压到 `lib/arm/`；
3. 新增 `com.huawei.vrhandle.compat.HvrPoseLibPath.get()`：优先返回**自身**
   `nativeLibraryDir`（并校验 `libvrpose.so` 存在），异常时 fallback 回原
   `r0.y0.j0()`；
4. `VrPoseJni.<clinit>` 里那一处 `invoke-static Lr0/y0;->j0()` 换成 helper，
   其余 4 个 `System.load` 与加载顺序完全不动。

产物 `com.huawei.vrhandle-pose.apk` 逐条校验：**858 条原样保留、2 条改动
（classes.dex / AndroidManifest.xml）、4 条新增、3 条旧签名剔除**，
用同一把 `hvr-compat-debug.jks`（alias `hvrcompat` / 口令 `android`）重签，
证书 `30094ded…814` 与其它三包一致。因为基线是华为原签，
`install -r` 会冲突，一键脚本已处理成「先试覆盖 → 失败则卸载重装」。
重签后 `com.huawei.android.permission.VR` 与
`com.huawei.vrservice.permission.VR` 自动变成 `granted=true`（原签拿不到）。
